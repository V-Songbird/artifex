# Output formats

A piece keeps one design box and one drawing function. [`core/render.js`](../../core/render.js) applies the selected playhead and scale without changing that design box.

## Interactive page and PNG

`npm run page` bundles the registered examples into `out/index.html`. The page provides example selection, seed and parameter controls, playback, PNG export at 1x, 4x, and 8x, and a film: MP4 export at 1x and 2x, or WebM export where the browser cannot encode the MP4 film. PNG and MP4 export redraw into an offscreen canvas at the requested resolution.

`npm run page -- ./piece.cjs` instead selects one external CommonJS piece and writes `piece-page.html` beside its source. It provides the same controls and exports. `npm run seeds -- ./piece.cjs 9 0.5` writes `piece-seeds.html` beside the source for comparison. See [external pieces](development.md#external-pieces) for invocation from another project, bundled dependency limits and parameter sweeps.

Playing a piece that declares sound plays its soundtrack with the picture. The first play of each solve renders the soundtrack with `renderSound`, as the MP4 export does, and plays it with one `AudioBufferSourceNode` from the transport's playhead, plus the context's output latency so sound and picture reach the viewer together. The audio context is made, or woken, in the play click, because browsers start audio only in a user gesture; a piece without sound never makes one. Pausing, scrubbing, a new seed and selecting another piece stop the sound; a parameter change while playing stops it and plays the new solve's soundtrack from the playhead; and when the transport wraps at the end, the sound starts again with it. A lap of the transport lasts the frame grid, frames / hz, as the soundtrack and the film do, even where the declared duration is no whole number of frames. The transport's clock still decides every drawn frame: the audio clock is read only to start the sound. This is for listening while working; the MP4 export renders its own soundtrack and is unaffected. A soundtrack that fails to render shows its error and the picture keeps playing.

A failed build has no renderable frame or export recipe. The page clears stale artwork, keeps the original error visible, and disables playback and exports until the piece rebuilds successfully or another valid piece is selected. It does not export partially built geometry.

The rendering API accepts any positive finite scale, subject to the destination surface's resource limits. Higher resolution should preserve the composition. Increase only the detail whose purpose depends on output resolution.

The page defaults to **CPU reference**. Raster-only pieces with an explicit
`webgpu-pixels` preview descriptor also expose **GPU preview**, an approximate
opaque pixel renderer. PNG, MP4, WebM, contact sheets and reference recipes always
use the original CPU `draw`; GPU mode does not change exported pixels or SVG
eligibility. Native browser support and an eligible hardware adapter are required.
Unavailable adapters, software adapters, insufficient limits, shader errors,
timeouts and device loss fall back to the current CPU frame. The status explains
the fallback and the renderer control can retry it.

GPU preview is capped at 4096 pixels per axis and 8,294,400 pixels total. It uses
a separate GPU canvas and includes the copy to the visible canvas in preview
timing. Those limits apply to preview only. See the [piece API](../apis/piece-api.md#optional-webgpu-pixel-preview)
for the supported authoring ABI, lifetime and measurement limits.

The `pixel-field` example evaluates seeded value noise, domain warp and advection
per output pixel. Its CPU renderer allocates ImageData at the destination raster
size; increasing export resolution increases CPU work and allocation. Its shader
implements the same field with float32 arithmetic. This example has no vector
output and its eight-second timeline is not a seamless loop.

## SVG

`renderVector(piece, options)` requires the piece to declare vector output. The vector surface supports path geometry and refuses unsupported raster operations by name. A raster-only piece remains a valid piece.

`npm run examples` writes SVG files for registered vector examples. The browser page also exposes SVG export when the selected piece declares it. Both embed the [replay manifest](#inspection-and-reproducibility), and for the same recipe the page's SVG button saves the bytes `renderVector` returns.

Ellipses and circles use native SVG `A` commands under a nonzero similarity transform: uniform scale with rotation or reflection. Reflection reverses the sweep; full circles use two arcs. Nonuniform scale, shear, singular transforms and radii that are zero or serialize as zero retain the cubic approximation. Coordinates and ellipse-axis rotation are rounded to four decimal places; nearly complete turns whose serialized endpoints coincide are split to keep them visible.

Identical input angles produce an empty sweep. Unequal whole-turn angles that normalize to zero retain a full traversal, matching the installed Edge comparison. SVG and Canvas antialiasing can differ for transformed ellipses. Stroke widths still use `sqrt(abs(det))`.

### Resolution-dependent detail in the inversion example

[`inversion.js`](../../examples/inversion.js) reflects circles in three disjoint circular mirrors using closed-form centers and radii, then emits arcs. Its depth-first traversal stops before drawing a circle whose diameter is below 1.4 output pixels. On native Canvas, it reads the current transform to account for PNG export scale; shared circles keep identical design coordinates and stroke widths as finer circles appear.

`VectorSurface.getTransform()` and the benchmark null surface return detached numeric `{a,b,c,d,e,f}` snapshots of the current affine transform. The snapshots are mutable, but editing one cannot change the surface; they have no `DOMMatrix` methods. Inversion uses this portable scale reader to add smaller circles at higher output scale without changing shared geometry. Surfaces without a reader use scale 1.

Ordinary SVG export uses the identity transform and retains the design-resolution cutoff. Enlarging that saved SVG preserves its geometry rather than regenerating detail. All outputs also stop after twelve reflections per root circle, bounding the traversal to 24,573 circles and thirteen live recursion levels even at extreme output scales.

## MP4

The page offers MP4 export for animated pieces at 1x and 2x of the design box. [`core/film.js`](../../core/film.js) draws every frame of `playheads(piece)` into an offscreen canvas and hands it to a WebCodecs `VideoEncoder` with the timestamp `i / hz`. Nothing is paced by the wall clock: a piece that draws slower than its frame rate takes longer to export and still keeps every frame at its declared time. When the piece declares `sound`, its soundtrack is rendered offline, levelled to -14 LUFS (see [soundtrack loudness](#soundtrack-loudness)) and encoded as AAC, or as Opus where the browser's `AudioEncoder` refuses AAC. The soundtrack is made alongside the frames: its rendering and encoding run off the page's thread, each frame yields once to the soundtrack's steps on that thread while it is being made, and the file is written once both are done. A soundtrack that fails stops the frames at the next one and fails the export with its own message. The file is H.264 video in an MP4 container, with the soundtrack as a second track.

The exporter requires `VideoEncoder` and `VideoFrame`, and for a piece with sound `AudioEncoder`, `AudioData` and `OfflineAudioContext` with AAC or Opus encoding. A piece that declares sound in a browser that encodes neither is refused before any frame is drawn, rather than exported silent. It declares the lowest H.264 level that fits the frame size and rate, trying High then Main profile, and rounds each side to the nearest even pixel count, at least 2, because 4:2:0 video needs one; an odd whole number of pixels rounds up.

AAC is tried first because more MP4 players play it. An Opus soundtrack follows the Opus-in-ISOBMFF encapsulation: an `Opus` sample entry at 48 kHz holding a `dOps` box converted from the encoder's OpusHead description (RFC 7845). The conversion keeps every field except PreSkip, writes them big-endian where OpusHead is little-endian, and sets the version to 0. Each packet's duration is read from its TOC byte. An encoder that describes no OpusHead fails the export, because nothing else records the pre-skip; it shows that only once it encodes, alongside the frames, which then stop. A player without Opus-in-MP4 support cannot play the soundtrack; check the player the film is delivered to.

Every film is limited-range BT.709. An encoder handed a canvas converts it to video colour its own way, and its choice of range can change between exports; platforms that re-encode uploads may mishandle a full-range tag. So every frame reaches the encoder as BT.709 limited-range video: luma in 16 to 235 and chroma in 16 to 240, BT.709 primaries, transfer and matrix, the canvas's sRGB-encoded values taken as BT.709's R'G'B', one chroma pair per 2x2 block from the block's average, and translucent pixels composited over black. The `colr` box always says primaries 1, transfer 1, matrix 1, full range off. The H.264 stream says the same, for a player or platform that reads the stream and ignores `colr`. Every sequence parameter set, in the encoder's `avcC` and any a sample repeats, gets a VUI video signal type: video format 5 (unspecified), full range off, and colour primaries, transfer characteristics and matrix coefficients 1 (ITU-T H.264, E.1.1). Every other field is copied bit for bit as the encoder wrote it, and an SPS without a VUI gets one that holds only the signal type. Edge's encoder writes a VUI without a signal type, which leaves such a player to infer limited range and guess the primaries, transfer and matrix. `readMp4` reports each SPS's colour description in the video track's `sps`.

The encoder converts the frames itself where the export proves that it writes exactly this. In installed Edge, an encoder handed a canvas that the browser draws on the GPU writes limited-range BT.709 within a level of the conversion above, and reports that colour space; handed a canvas kept in memory, as `willReadFrequently` asks, it writes full range and reports that. The browser moves a canvas to memory by itself: three `getImageData` calls on one were enough, and from the next frame the film was full range, with a new keyframe and a new reported colour space. So the exporter hands the encoder a WebGL2 copy of each drawn frame, which stays on the GPU whatever happens to the canvas it copies, and reads nothing back. A test pattern of solid cells goes through the same copy and encoder before the first frame and after the last, and is decoded in software; every cell must be within two levels of the CPU conversion, and every colour space the encoder reports must say BT.709 primaries and matrix with limited range. The encoder must also return an output for every frame. Chromium's Media Foundation encoder drops a frame it is handed as a texture, with no output and no error, when it cannot take the texture's lock within 100 ms, which load can cause; it copies a frame handed over in memory, as the conversion does, without that lock. A film that fails any of these, or that the route cannot finish, is encoded again, converted as below. The route needs WebGL2, `VideoDecoder` with software decoding to I420, and `EncodedVideoChunk`. The test pattern is not part of the film, and the tag and the file check are the same on every route.

Otherwise, where WebGL2 is available, a shader converts a texture copy of the drawn frame and one readback returns both planes. Before an export uses it, it must reproduce the CPU conversion on a test pattern within one level; otherwise, or without WebGL2, the CPU converts each frame read back from a canvas kept in memory for the whole export, so the browser never switches that canvas's rasterizer part-way through a film. `report.conversion` names the route, `encoder`, `gpu` or `cpu`, and `report.convertMs` its time: on the GPU and CPU routes it includes waiting for each frame to finish drawing, and on the encoder route the two test patterns. Reading every frame back costs time: in installed Edge the GPU route took 2.5 to 8.5 ms per frame at 1x and 2x. The encoder route's whole exports, test patterns and soundtrack included, took 1 to 32% less time than the GPU route's, medians of five on a loaded machine: drift 2.3 s against 2.9 s at 1x and 2.7 s against 3.8 s at 2x, while settle, whose soundtrack takes most of its export, gained 1%. Decoded, its films matched the GPU route's against the drawn frames within 0.2 dB, and the colour chart's patches were within one level of the drawing on both.

Every film carries its replay manifest, so a saved film names the piece, seed and parameters that made it. The manifest is the solve's, as an SVG carries it, with `film: { frames, hz, loop, scale }` where an SVG has the playhead `t`: the number of frames drawn, the frame rate, whether the timeline loops, which puts frame `i` at playhead `i / frames` rather than `i / (frames - 1)`, and the export scale, because a piece may draw finer detail at a higher scale. It is stored in `moov/udta`, the user-data box, as a `uuid` box with extended type `8b2fd966-e923-4330-a28e-6d82587d1ec9`: the box header, the 16-byte extended type, then the manifest as JSON to the end of the box. The JSON is ASCII; any other character is written as a `\uXXXX` escape, so the bytes are also valid UTF-8. ISO/IEC 14496-12 reserves `uuid` for private box types and requires readers to skip box types they do not know, so a player ignores it; installed Edge decodes films that carry it. The box sits in `moov`, before the media data: it moves the chunk offsets and leaves every sample byte unchanged. The readout example's film spends 209 bytes on it. Tag editors and remuxing tools may drop it. `readMp4` returns it as `manifest`, or `null` for a file without one.

Before returning a result, the exporter reads the finished bytes back: exactly one H.264 track, every declared frame, uniform frame durations on the frame grid, the requested size, a first keyframe, the limited-range BT.709 colour tag and the same colour description in every sequence parameter set, every sample inside the media data, the replay manifest equal to the one the export drew with, a movie and track headers lasting the film, and, with sound, one AAC track or one Opus track with its `dOps`, whose packets after its priming cover the whole film and run past it by less than two packets, and one edit that skips exactly the priming the encoder reported and lasts the film. A failed check displays an error and nothing is saved. A film refused for its frame count names the colour route that ran and the timestamps, in microseconds, of the first three frames its encoder returned nothing for. `window.__artifex.film({ scale })` returns the report and blob without saving a file; the report includes draw, conversion, encode, soundtrack and total times and the ratio to real time, where `soundMs` is the soundtrack's own time, which runs alongside the frames, and `encodeWaitMs` includes each frame's yield to it, `report.sound.codec` names the soundtrack's sample entry, `mp4a` or `Opus`, `report.sound` also gives the soundtrack's level (see [soundtrack loudness](#soundtrack-loudness)), and `report.manifest` is the manifest read from the file.

After an MP4 export the page's note reads those facts from the report: the frame count, size, length and bytes, the soundtrack's codec (AAC for `mp4a`, or Opus), and where the colour was converted: by the encoder, whose range the export proved with test patterns, or on the `GPU` or `CPU`, with `report.convertMs`. For an Opus soundtrack it adds that the browser encodes no AAC, and that the film should be played where Opus in MP4 is supported, or it plays silent.

`npm run browser` exports a film this way in installed Edge for every example that declares sound, or for the first with a timeline when none does. For each film it requires the page to offer MP4 and hide WebM, decodes the film, requires the first, middle and last decoded frames to resemble their own drawn frames at least as closely as their neighbours (a held frame ties with an identical neighbour) and at 30 dB or better, and requires a declared soundtrack to decode to exactly the film's length, within one sample, to follow a fresh render at the export's gain for 1024 samples from its first sound, where a codec's priming would swallow or shift it, at 10 dB signal to error or better, to measure -14 LUFS or peak at -1 dBTP, within 0.1, once decoded, and two more renders of it to hold the same bits in every sample, since the examples sum their voices two at a time and Edge then renders them identically (see the [piece API](../apis/piece-api.md#soundtrack)). It finds the manifest in the film's bytes with its own scan rather than `readMp4`, and requires it to equal the page's `manifest()` with the frame grid in place of the playhead. It exercises the soundtrack codec the browser chooses, which is AAC wherever AAC encodes, as in installed Edge, and the colour conversion the browser supports, which is the encoder route there; each film's report names it, and a film that falls back to the GPU or CPU conversion fails the check unless `--allow-fallback` accepts it on a machine without a usable GPU. Its summary line names, for every film, the soundtrack codec and the colour route. The Opus path, the CPU conversion and the encoder route's refusals are checked in Node against controlled encoders, and the Opus path and the CPU conversion also in installed Edge on one film each, by `npm run browser -- --force no-aac`, which refuses AAC so the film carries Opus, and `--force no-webgl2`, which hides WebGL2, so neither the encoder route's WebGL2 copy nor the GPU conversion is available and the CPU converts (see the [development guide](development.md#what-verification-establishes)). Decoded frames and sound are compared within the tested browser; they are not byte-identical to the drawing. In installed Edge 153 the examples' soundtracks followed their render from their first sound at 29 to 52 dB, AAC and Opus.

### Film length and the soundtrack's edit list

A film lasts exactly its frames, `frames / hz`. The movie counts time in the video track's own timescale, so the movie header, both track headers and the soundtrack's edit all state that length without rounding. A 2 s film's movie lasts 48000 ticks of 24000 per second.

An encoder's soundtrack does not start and end with the film. It opens with priming, samples the encoder needs to warm up, and its last packet runs past the film by up to one packet. Each soundtrack therefore carries one edit (`edts/elst`). Its `media_time` skips the priming, and its `segment_duration` plays exactly the film's length, with media rate 1. The encoded samples themselves are all kept.

For Opus, the priming is the pre-skip in the encoder's OpusHead, 312 samples (6.5 ms) from Edge's encoder. The Opus-in-ISOBMFF specification makes the edit list the trim and calls `dOps` PreSkip informative, so PreSkip is written as 0. Chromium trims by both the edit and PreSkip; a film that repeated the pre-skip in PreSkip would lose its first 6.5 ms there. A reader that trims only by PreSkip and ignores the edit list, contrary to the specification, plays the 312 warm-up samples, starting the sound 6.5 ms late.

For AAC, no decoder rebuilds the first half of a stream's first 1024-sample frame, and Edge's AAC encoder starts the soundtrack in that frame without reporting any priming: it stamps its first packet at zero. Encoded that way, the soundtrack's first ~500 samples decode to silence. So the exporter feeds the encoder 2112 samples of silence ahead of the soundtrack, the conventional AAC priming, and the edit's `media_time` skips them, together with any priming an encoder reports by stamping its first packet before zero. The lead is no whole number of packets on purpose: in Edge's `<video>` element, an edit that starts on a packet boundary starts that packet without the one before it, and the first ~500 samples are lost again. A player that ignores edit lists starts an AAC soundtrack 2112 samples late, 44 ms at 48 kHz; one that assumes the conventional 2112-sample priming without an edit list comes out exact.

In installed Edge 153, both `decodeAudioData` and a `<video>` element play an exported test film's soundtrack from its first sample to the film's last, AAC and Opus alike, and its first 128 samples decode as faithfully as the rest. Without the lead, both paths lost the first ~500 samples of an AAC soundtrack, at 48 and 44.1 kHz; the element's output stayed exactly zero up to sample 448, as it does for a bare ADTS stream. Firefox, Safari and FFmpeg-based players were not tested.

### Soundtrack loudness

Every film's soundtrack is levelled by one static gain: up to -14 LUFS integrated loudness, unless its true peak would pass -1 dBTP first, where the gain stops and the film stays quieter than -14 LUFS. Platforms that play films turn a loud upload down to about -14 LUFS and barely raise a quiet one, so a film mixed quiet would stay quiet beside everything else. No compressor or limiter is applied, so the piece's dynamics are kept; a mix whose peaks stand far above its body ends quieter than the target.

The soundtrack is measured as rendered, before encoding, to ITU-R BS.1770-4. Loudness is the mean square of the K-weighted signal, a high shelf of about +4 dB above 1.5 kHz and then a high-pass near 38 Hz, over 400 ms blocks that overlap by 75%, gated at -70 LUFS and then 10 LU below the mean of the blocks that passed. Every mean is of power, and a mono or stereo channel is weighted 1. True peak is the largest magnitude after four-times oversampling with the standard's Annex 2 filter. [`core/film.js`](../../core/film.js) exports `measureLoudness(buffer)` and `normalizeLoudness(buffer)` for an AudioBuffer-shaped soundtrack, and the page exposes the meter as `window.__artifex.loudness`. The Node tests hold the K-weighting to the standard's 48 kHz coefficients, the gating to EBU Tech 3341's cases within 0.1 LU, and true peak between samples to its +0.2 / -0.4 dB.

A soundtrack with no block above -70 LUFS has no loudness to set: it keeps its level, and the report gives its loudness as `null`. A soundtrack holding a sample that is not a finite number is refused, and no film is saved.

`report.sound.measured` gives `lufs` and `dbtp` as rendered, `report.sound.gain` the gain in dB, and `report.sound.lufs` and `report.sound.dbtp` the level the soundtrack is encoded at. In installed Edge 153 the examples' films measured:

| example | as rendered | gain | encoded | decoded |
| --- | --- | --- | --- | --- |
| readout | -22.00 LUFS, -10.77 dBTP | +8.00 dB | -14.00 LUFS, -2.76 dBTP | -14.01 LUFS, -2.77 dBTP |
| settle | -27.74 LUFS, -14.69 dBTP | +13.69 dB, at the ceiling | -14.05 LUFS, -1.00 dBTP | -14.06 LUFS, -1.03 dBTP |
| cues | -24.50 LUFS, -12.11 dBTP | +10.50 dB | -14.00 LUFS, -1.61 dBTP | -14.01 LUFS, -1.62 dBTP |

AAC at 192 kbps moved loudness by at most 0.01 LU and true peak by at most 0.03 dB in these films.

The same films exported with AAC refused, so that each soundtrack took the Opus path at 192 kbps as in a browser without AAC, measured in installed Edge 153, twice with the same result:

| example | encoded | decoded Opus | true-peak change |
| --- | --- | --- | --- |
| readout | -14.00 LUFS, -2.76 dBTP | -14.01 LUFS, -2.69 dBTP | +0.07 dB |
| settle | -14.05 LUFS, -1.00 dBTP | -14.04 LUFS, -0.94 dBTP | +0.06 dB |

Opus moved loudness by at most 0.01 LU and raised true peak by up to 0.14 dB, more than AAC. A film whose gain stops at the ceiling, as settle's does, therefore decodes about 0.06 dB above -1 dBTP when its soundtrack is Opus. The ceiling is applied to the rendered soundtrack, before encoding, and the gain rule does not allow for the codec. Each decoded Opus soundtrack lasted exactly its film, 336000, 288000 and 384000 samples.

### Which film the page offers

For an animated piece, the page asks `VideoEncoder.isConfigSupported` about the H.264 configuration the export uses at 1x. `filmConfig(piece, VideoEncoder, { scale })` in [`core/film.js`](../../core/film.js) makes that choice for both the question and the export. The page asks once per design size and frame rate. It starts and draws without waiting for the answer, and shows the MP4 controls until the answer arrives. Where the encoder accepts no configuration, or the browser has no `VideoEncoder` or `VideoFrame`, the page hides the MP4 controls and offers the WebM export instead. A still offers no film. Either film control stays disabled until the piece has a valid build.

For a piece that declares sound, the page also asks `AudioEncoder.isConfigSupported` about the soundtrack configuration the export uses: AAC, then Opus, at 48 kHz stereo and 192 kbit/s. `soundConfig(AudioEncoder)` in [`core/film.js`](../../core/film.js) makes that choice for both the question and the export, and the page asks it once. The MP4 export never writes a film without its declared soundtrack. So where the browser encodes the H.264 but neither AAC nor Opus, or has no `AudioEncoder` or `AudioData`, the page hides the MP4 controls and offers the WebM export with a note that the film is silent. A piece without sound is never asked about, so it keeps its MP4. Neither question holds up start-up or drawing.

`window.__artifex.filmFormat()` resolves to `'mp4'`, `'webm'` or `null` (a still) once the page has applied the answers for the selected piece. `window.__artifex.filmOffer()` resolves to `{ format, reason }` from the same decision, the one the WebM note is written from. The reason is `'h264'` where the H.264 film cannot be encoded, even if the soundtrack could not be either; `'soundtrack'` where it can but neither AAC nor Opus encodes the declared soundtrack; `'still'` for a still; and `null` with the MP4. A script can tell the silent case apart without reading the note. The scripted exports do not follow the controls: `film()` still refuses by name where H.264 cannot encode the film or neither AAC nor Opus encodes its declared soundtrack, and `video()` still records wherever its recorder APIs exist, so existing scripts keep working. A 2x MP4 can still be refused where 1x encodes; its error names the size and asks for a smaller scale.

## WebM

WebM is the fallback film: the page offers it only for an animated piece whose MP4 this browser cannot encode (see [which film the page offers](#which-film-the-page-offers)). The implementation requires `MediaStreamTrackGenerator`, `VideoFrame`, and `MediaRecorder` with VP8 WebM support. Availability must be checked in the browser used for delivery. It carries no soundtrack, even for a piece that declares one.

The exporter walks the piece's frame grid and paces frames at its declared rate, because `MediaRecorder` stamps frames by the wall clock. A piece whose frames take longer than their budget to draw and encode therefore cannot be recorded; the export measures how far it fell behind its schedule and says so, naming MP4 from a browser that encodes H.264 as the export that keeps every frame. Other work on the same machine can make a light piece miss its schedule too. Rendering and encoding are measured separately. Before returning a result, it parses the recorded WebM blocks and validates frame count and spacing. A rejected export displays an error instead of downloading a result.

`MediaRecorder` writes a live WebM. In installed Edge its Segment has an unknown size and its Info Duration is one TimecodeScale unit, so a player reports 0.001 s and cannot seek. Once the recorded file passes its checks, the exporter writes the film's length, `frames / hz`, over that Duration in the file's own units. A file with no Duration gets one at the end of Info, and Info grows by its eleven bytes. Every other byte is the recorder's, apart from the stored positions an insertion moves. In installed Edge 153, a recorded 144-frame film at 24 Hz reported 0.001 s and a seek to its middle frame stopped at 2.25 s; with the Duration written it reported 6 s and seeks to its first, middle and last frames each showed the frame asked for.

A WebM stores some positions as byte offsets from the start of its Segment's data. When Edge's recorder stops, it writes Cues after the last Cluster, and each CuePoint stores the position of its Cluster. A recording whose data is collected only at stop also starts with a SeekHead, which stores the positions of Info, Tracks, the first Cluster and the Cues. The page asks for data while it records, so its recordings carry Cues and no SeekHead. Each insertion, a Duration or the recipe's `Tags` below, moves every SeekPosition and CueClusterPosition at or past it by its length. A position that outgrows its field is written wider, which grows its SeekHead or Cues and moves what follows them; this repeats until no field grows, and a Segment of known size grows by everything added. The first SeekHead also gets a Seek entry for the recipe's `Tags`, so a reader that finds elements through it finds the recipe. A CRC-32 that opens an element covers the rest of that element's data. When the Duration is written, a CRC-32 opening Info is computed again. When an insertion rebuilds a SeekHead or Cues, a CRC-32 opening it or one of its parts is computed again over the rebuilt element. Each is stored little-endian, as EBML stores it. A file that also stores a Cluster Position, a CueCodecState or a CueReference, or has a CRC-32 that does not open its element or covers the whole Segment, is refused by name rather than saved with a stale value. Installed Edge 153 showed the same frames at each seek whether the Cues had moved or not, so a player there does not show this; the Node tests check the moved positions against the file's bytes.

The exporter copies each drawn frame onto a second canvas that nothing reads back, and hands the recorder that copy without its alpha plane (`alpha: 'discard'`), so translucent pixels arrive composited over black, as in the MP4. Edge's recorder writes a Colour element at the first frame and codes each frame by the backing of the canvas it records. A canvas on the GPU gives limited-range BT.709 (matrix, transfer and primaries 1, range 1); a canvas kept in memory gives full range (range 2, transfer 13). Three `getImageData` calls move a canvas to memory for good, so a piece that read its own canvas back from mid-film would switch the coding to full range under a Colour element that still says limited. Recording the copy keeps the whole film on the backing it started with. Measured in installed Edge 153 on a colour chart of flat patches, 20 frames at 10 Hz, decoded with `VideoDecoder` and read against the drawn values:

| The piece's drawing canvas | Coded, recording the copy | Colour element | Patches read back | Recording the drawing canvas itself |
| --- | --- | --- | --- | --- |
| never read back | BT.709 limited | limited | within 2 levels | the same |
| read back from the first frame | BT.709 limited | limited | within 2 levels | BT.709 full range, tagged full, within 3 levels |
| read back from frame 11 | BT.709 limited throughout, one keyframe | limited | within 1 level | full range from frame 11 under a limited tag: 16 read as 0, 235 as 255 |

In headless Edge 153, drawing a `<video>` element onto a canvas converted a software-decoded (I420) frame's blue up to 12 levels off, while drawing a `VideoFrame` made from the same element was within 2 levels. Which decoder Edge used varied between films whose frames were byte-identical. Read a film's levels through a `VideoFrame` or a decoder, not through `drawImage` of the element.

A timeline with one frame still requires exactly one recorded frame, but has no spacing interval to validate. Its report uses zero for the gap statistics and `1 / hz` seconds for the frame's declared interval. This reported duration does not independently measure playback duration in a video player.

`window.__artifex.video()` returns the export report and blob without saving a file, whichever film the page offers. The page's video button downloads that result. A still has no video timeline and cannot use this exporter.

The Node page tests cover both offers with stand-in encoders, and the WebM export's frames and saved duration with a stand-in recorder. Recordings built in both of Edge's shapes, and one with Cues before its first Cluster, check the moved positions, the Seek entry for the `Tags` and the CRC-32s of Info, a SeekHead and Cues. `npm run browser` exercises the MP4 offer, because installed Edge encodes H.264. `npm run browser -- --force no-h264` refuses H.264 in the page before it loads, requires the WebM offer for that reason, and records one film whose saved file must decode, last `frames / hz` seconds in Edge's video element, and hold every frame, evenly spaced; a heavily loaded machine can make that recording fall behind its schedule, and the page then refuses it, so the run records again, at most three recordings in all, and names each refusal. A completed build or Node suite does not verify the browser's encoder, download behavior, or how the saved video looks. Validate those in the target browser using the saved file.

## Inspection and reproducibility

The page exposes `window.__artifex` for selecting examples, reading current state, inspecting named build stages, and retrieving replay metadata. `inspect(stage)` returns a summary instead of copying raw typed arrays or geometry.

The replay manifest records the library version, piece name, seed, parameters, dimensions and declared outputs. It contains neither the timeline definition nor a copy of the piece source. Replaying it requires the corresponding code, input data, and execution environment. These carry it:

| Carrier | Where | Adds |
| --- | --- | --- |
| The page's `manifest()` | its return value | the quantized playhead `t` |
| An SVG, from `renderVector` or the page's SVG button | a `<metadata id="artifex-manifest">` element before the drawing, holding the manifest as JSON with `&`, `<`, `>` and `"` escaped | `t` |
| An MP4 film | a `uuid` box in `moov/udta` (see [MP4](#mp4)) | `film: { frames, hz, loop, scale }` |
| A PNG saved from the page, at any scale | an `iTXt` chunk before `IEND`, keyword `artifex-manifest`, no compression, empty language tag and translated keyword, holding the manifest as JSON | `t` and the export `scale` |
| A WebM film from the fallback | a `Tags` element before the first `Cluster`: one `Tag` with empty `Targets` (the whole film) and one `SimpleTag`, `TagName` `ARTIFEX_MANIFEST` and `TagString` holding the manifest as JSON | `film: { frames, hz, loop, scale: 1 }`, as the MP4 of the same film |

The WebM's tag is added to the saved file after its Duration. Every Cluster and Block keeps its bytes, and the stored positions past the tag move with them (see [WebM](#webm)). Players skip tags they do not use. `webmManifest(bytes)` in [`tools/build-page.js`](../../tools/build-page.js) reads it back, returns `null` for a WebM without one, and throws by name for a file that ends inside the element. `video()` also returns it as `report.manifest`.

The PNG's JSON is ASCII: any other character is written as a `\uXXXX` escape, as in a film, so it is also the UTF-8 that `iTXt` requires. The chunk is added to the bytes the browser encoded; removing it gives back those bytes exactly, and no pixel changes. Image tools that rewrite a PNG may drop it. `pngManifest(bytes)` in [`tools/build-page.js`](../../tools/build-page.js) reads it back, or returns `null` for a PNG without one. It reads only inside the chunk, and throws by name for a file that ends inside the chunk or a chunk without its text.

### Replaying a saved file

`npm run replay -- <file>` reads the manifest back from a saved SVG, PNG, MP4 film or WebM film and draws its recipe again. The piece is the registered example the manifest names, looked up as an own property, or the module passed with `--piece`; a module named inside the file is never loaded. A file made by another library version, for another piece, or for a box or outputs the piece no longer declares is refused before anything is drawn, and so is a PNG whose size, scale or playhead no longer matches, and a film whose frame grid (frame count, rate and loop), size or number of frames no longer matches. Every refusal and every mismatch exits nonzero and names the first difference.

An SVG is drawn again in Node and must be byte-identical; a difference is named by its first byte. `svgManifest(svg)` in [`core/surface-vector.js`](../../core/surface-vector.js) reads the recipe from any SVG, whether `renderVector` or the page's SVG button wrote it. The page draws its SVG with the browser's JavaScript engine, and replay draws it again with Node's. So for a page SVG, byte identity also means the two engines computed the same numbers, which ECMAScript does not promise (see [verification culture](verification-culture.md)). A differing byte cannot tell a changed recipe from a different engine. In installed Edge 153, the page's SVGs of settle, readout, cues, contours and inversion replayed byte-identical in Node 22.

A PNG is decoded in installed Edge and compared at full size, every channel and alpha included. It is compared with the still drawn again at its recipe, playhead and scale on a GPU canvas, as the page's PNG button draws, and with the frames on either side. It matches when every pixel is identical. Otherwise it must be within 40 dB PSNR of its redraw and at least as close to it as to either neighbour. In installed Edge 153, the page's PNGs of settle at 1x and 4x, drift and readout were identical to their redraws, and their neighbouring frames sat at 32 to 46 dB. A settle PNG whose recipe named seed 9 came out at 17 dB. A drift PNG whose playhead named the next frame was refused, because it was identical to the frame it was drawn at.

An MP4 film is decoded in installed Edge, through the same driver as `npm run browser`, and compared at up to 24 frames spread evenly, first and last included. Each decoded frame must be within 30 dB PSNR of its redraw on a GPU canvas at the film's scale, compared at 240 pixels wide with drawn pixels over black, and at least as close to its own redraw as to either neighbour's; a held frame ties with an identical neighbour. In installed Edge, every example's own film decoded at 39 to 54 dB from its redraws, and a drift film drawn with seed 9 whose manifest said 8 was refused, its frames falling from 36 to 17 dB.

A WebM is compared as an MP4 film is, with the same floor and rule. Each frame is sought midway through its own block, from the file's block times: the recorder stamps blocks by the wall clock, so a seek on the frame grid can land on a neighbour. Each decoded frame is read through a `VideoFrame`. In installed Edge 153, the page's WebMs of drift (240 frames) and readout (168) matched at 43 to 52 dB and 40 to 45 dB. A drift WebM whose recipe named the next seed fell from 56 to 18 dB and was refused.

An MP4 film's soundtrack is compared in the same page, after its pictures. A WebM carries no soundtrack, so replay compares its pictures only. The film and its piece must agree on whether there is one, and it must be AAC or Opus, the only codecs the export writes. The film's soundtrack is decoded as a player hears it, trimmed by its edit list, and must have the channels and the length, to the sample, of the recipe's soundtrack rendered and levelled as the export levels it (see [soundtrack loudness](#soundtrack-loudness)). Each block of 1024 samples must then be within 25 dB of the render for AAC, or 15 dB for Opus, unless the two differ by less than -60 dBFS, where the codec's own noise decides. The first block outside is named by its time. In installed Edge 153, every judged block of the readout, cues and settle films decoded at 34.8 dB or better as AAC and 23.6 dB or better as Opus, and all six films replayed as matches. A film whose piece drew the same pictures with its tone moved from 440 to 466 Hz differed at its first block, at -3.5 dB, and the same piece's film without a soundtrack was named as carrying none. The next seed's soundtrack of readout and settle came within -7 dB of their films. Cues, whose soundtrack barely follows the seed, came within 24.2 dB as AAC and 20.1 dB as Opus, so a change that small passes as Opus.

A recipe that draws nearly the same pictures, such as a small parameter change, can pass a film comparison within that tolerance, and a soundtrack change smaller than its codec's noise passes the soundtrack comparison. An SVG rendered with a `background` option replays without it and differs, because the manifest does not record it.

Review multiple seeds in rendered output. SVG equality, frame counts, and pixel statistics establish different properties; none establishes artistic quality by itself.
